# L07 Ray Systems Lab — Report

## Question

When is distributed execution with Ray a net gain, and how do task granularity, data placement
(object store), actor placement (logical resources) and failure handling change the answer?
Secondary: what do Ray Data, Ray Train and Ray Serve add on top of Ray Core, and where does their
responsibility stop relative to the training/inference engine?

## Environment

Single workstation (`hostname kirc`): Intel i9-12900KS (24 threads), 110 GiB RAM; GPUs: RTX A6000
48 GB (device 0, not used by this lab) and RTX PRO 6000 Blackwell 96 GB (device 1, PCIe, no NVLink).
During the pilots the Blackwell GPU was **shared** with pre-existing vLLM servers holding ~90 GB,
leaving ~5 GB; the CPU was shared with other experiments. Software: Python 3.10.12, Ray 2.53.0,
torch 2.11.0+cu130, transformers 5.7.0. Exact versions, driver, topology and git commit are in each
run's `manifest.json` (copied to `results/<experiment>/manifest.json`).

## Hypotheses

1. Per-task overhead of Ray is of the order of 0.1–1 ms, so tasks below ~1 ms of work are slower
   than a local loop; chunking restores the speed-up.
2. Passing a large argument by value to K tasks costs K serialisations; `ray.put` once is ~K× cheaper.
3. Filling the object store beyond its size triggers spilling, visible as slower `get` and MiB on disk;
   bounding in-flight work prevents it.
4. `num_gpus` fractions are accounting only: co-located actors can allocate beyond their share and
   nvidia-smi reflects the sum of real allocations (plus one CUDA context per process).
5. With retries enabled, worker death yields at-least-once execution: side effects before the crash
   are duplicated unless the sink is idempotent; with an idempotent keyed sink the output equals the
   input set exactly.
6. Stateful actors beat per-call model loading by the ratio of load time to inference time;
   batching inside the actor adds a further gain.
7. In Ray Data, a slow preprocessing stage starves the generator and shows up as the dominant stage
   in `ds.stats()`; Ray Serve replicas scale request throughput for a fixed-latency model nearly
   linearly, and Serve-level batching only helps a model that benefits from batching.

## Baseline

* Sequential Python loop (task overhead); argument by value (object store); `naive` policy with no
  retries (failures); task-per-call model loading (actors); 1 replica, no batching (Serve).

## Change

One variable per experiment: backend / granularity; by-reference passing and store size;
`max_restarts` + `max_task_retries` + idempotent sink; actor pool and batch size; replicas and
`@serve.batch` window.

## Method

Each script creates a `Run` (manifest + config + records + summary) under
`runs/L07_ray_systems/`. CPU work is a busy-wait of controlled duration so granularity is exact.
Models are `HuggingFaceTB/SmolLM2-135M-Instruct` (tiny, so an actor pool fits in the GPU budget;
CPU pilots use it too). Load tests are closed-loop with a fixed number of requests per condition.
Results reported below are single runs (repeats = 2 for task overhead, min taken) on a shared host:
they are pilot numbers; the comparisons inside one run share the same noise.

## Bottleneck analysis

* **Scheduling overhead** is the binding constraint below ~1 ms of work per task; it is paid per
  task, so chunking is the fix, not more workers. `multiprocessing` has ~10× lower per-item overhead
  than Ray tasks on one node because it has no scheduler or object store, which is the price of
  Ray's generality.
* **Serialisation and the object store** dominate when large arguments are passed by value; the
  12.4× gain from `ray.put` is the number of consumers minus one serialisations avoided. Spilling
  converts memory pressure into disk latency (hundreds of ms per object here) instead of failures;
  backpressure removes it entirely at the cost of a bounded producer.
* **Logical resources** do not isolate memory: three quarter-GPU actors consumed 3.2 GB on a GPU
  with only ~5 GB free; a fourth would have OOM-ed all of them. Each process also pays ~0.5 GB of
  CUDA context, which argues for fewer, batched actors.
* **Fault tolerance** moves the bottleneck from availability to semantics: Ray recovers an actor
  in ~0.26 s, but the application decides whether the recovered work is duplicated.
* **Model loading** is the bottleneck of task-per-call inference (64 × 1.77 s of the 30.6 s);
  actors remove it, batching then amortises per-call overhead further (4.5× total).
* **Ray Data**: batching inside the generator actor is the lever (3.2×); the slow-preprocess
  condition was confounded by external CPU load, which the per-operator stats exposed.
* **Ray Serve**: for a compute-bound replica, concurrency only adds queueing (p50 grows linearly);
  throughput comes from replicas (when there are spare cores/GPUs) or from batching (when the model
  is sub-linear in batch size). Replicas and Serve-level batching compete for the same requests, so
  on a single host batching in one replica beat two batched replicas.

## Limits

* Single node: no network transfers, no cross-node object fetches, no node loss.
* Shared CPU and GPU during the pilots; absolute numbers are not reusable as baselines.
* Tiny model for the actor / Serve / Data experiments; ratios change with a larger model.
* Ray Serve routing was measured with HF `generate` and a fake model, not in front of vLLM.
