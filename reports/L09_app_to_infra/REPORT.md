# L09 Application-to-Infrastructure Demo — Report

## Question

How do application-level choices (retrieval depth, reranking, tool use, claim verification) change
task success and the per-stage latency of a RAG/agent workload, and how are those traces joined to
the serving metrics of the lower layers?

## Environment

Same workstation as L07. The 0.5B generator, the bge-small embedder and the bge-reranker-base
cross-encoder ran on the shared RTX PRO 6000 Blackwell (device 1, ~5 GB free) with HF transformers
(no engine, no batching, greedy decoding). Software: Python 3.10.12, torch 2.11.0+cu130,
transformers 5.7.0, sentence-transformers 5.2.2, faiss-cpu 1.14.3. Models: `Qwen/Qwen2.5-0.5B-Instruct`,
`BAAI/bge-small-en-v1.5`, `BAAI/bge-reranker-base`. Data: `rag-datasets/rag-mini-wikipedia`
(3 200 passages; 100 shuffled test questions, seed 0 for RAG, seed 1 for the agent). Exact details
are in each run's `manifest.json` under `results/`.

## Hypotheses

1. Cross-encoder reranking raises the chance that the answer is in the top-3 context and hence EM/F1,
   at the cost of ~10 extra small forward passes per question.
2. Model compute dominates per-request latency; retrieval over a 3 200-passage flat index is negligible.
3. A tool-calling loop lets the small model solve arithmetic it cannot do alone, at the cost of
   2–3× more model calls per task and longer prompts.
4. Claim verification reduces unsupported statements; in `remove` mode it can also delete correct
   answers whose evidence was not retrieved, so success may fall while precision rises.

## Baseline

RAG: retrieve top-10 by cosine, take top-3 as context, no reranking. Agent: verification off.

## Change

RAG: rerank the 10 candidates with the cross-encoder and keep the top-3. Agent: verification in
`flag` mode (append a warning) and `remove` mode (drop unsupported sentences).

## Method

`applications/rag/evaluate.py` runs both variants on the same 100 questions with the same
generator, scoring EM and token-F1 with SQuAD normalisation, bootstrap 95% CI on EM (1 000
resamples), recall@10 (answer string in any candidate) and recall-in-context (answer string in the
passages shown to the model). `applications/agent/evaluate.py` runs 40 QA questions plus 10
generated arithmetic questions through the JSON-action agent (max 3 steps) for each verification
mode; success is F1 ≥ 0.5 for QA and exact number for arithmetic. Every stage is a traced span;
latencies are means per question.

## Bottleneck analysis

* **Model compute dominates** both workloads (85% of RAG latency, 99% of agent latency). Nothing
  on the retrieval side is worth optimising until the generator is served by an engine with
  batching and prefix caching; that is the L02/L03 link.
* **Reranking is not free and not always positive.** +16 ms per question (10 cross-encoder pairs)
  and, for this model and dataset, a lower EM despite equal-or-better context recall: the generator
  is sensitive to passage order. The decision rule is to measure recall-in-context and EM together,
  not to assume the reranker helps.
* **Agent loops multiply cost super-linearly**: 3 model calls and 3.4× prompt tokens per task,
  because each step re-sends the growing conversation. Prefix caching recovers part of that cost
  (the conversation prefix is shared across steps), which is why the agent workload is the right
  one to put in front of a caching engine.
* **Protocol failures are a capacity problem**: the 0.5B model truncates its JSON and loops on
  tool calls. The salvage parser and forced-final fallback reduced the parse-failure rate from
  15/40 to 13/40 but did not change the conclusion; a larger model or native tool calling is the
  fix, not more parsing.
* **Verification** is cheap when evidence is already in memory (12 ms) and acted only on wrong
  answers here, i.e. it raised precision without hurting recall on this sample; its real cost in a
  served system is the extra cross-encoder or judge call per claim.

## Limits

* One model size, one subset, single run: CIs are wide (±0.09 EM at n = 100).
* HF generation without an engine: no batching, no prefix cache, so the serving-side link (cache
  hit rate, TTFT under load) is not measured here; the `--generator endpoint` path exists for it.
* Verification uses relevance scores as an entailment proxy.
* Small models follow the JSON action protocol unreliably; `parse-fail rate` is reported separately.
